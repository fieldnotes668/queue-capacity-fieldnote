ENGINEERING NOTE · 11 NOVEMBER 2026

Polling is traffic too

A status page that checks every few seconds can look quiet to the person reading it. Across many open tabs, those checks become a workload of their own.

The arithmetic is simple enough to make visible before choosing an interval. The hard part is deciding which updates need to be seen quickly and when checking should stop.

A steady-state estimate

Synthetic model. No requests are sent. One client means one active polling loop, not necessarily one person.

Read the assumptions first

The estimate is clients × 60 ÷ interval seconds. It assumes every client keeps polling at the same fixed interval for a full minute. It omits retries, initial page loads, caching, browser scheduling, disconnected clients, and request duration.

It is an average request rate, not a peak-load forecast. If clients start together, requests can arrive in a burst even when the average is modest. Randomizing schedules can spread work, but it does not remove the work itself.

Start with the state transition

List the events that could actually change the page. A completed workflow may not need continuing checks. A long-running process may tolerate a slower interval after a period without change. A user returning to the tab may need a fresh observation immediately.

Do not let every component create an independent loop for the same resource. A screen with three widgets can accidentally become three clients. Share an observation where the architecture allows it, and cancel obsolete work when the context changes.

Keep uncertainty visible

A failed check does not mean the underlying operation failed. Keep the last observation's time and the fetch error separate from the business state. Avoid replacing “processing” with “rejected” merely because the network request timed out.

Our CardNaro work makes status clarity a useful design question. This calculator is an independent teaching model, not a measurement of CardNaro traffic or a description of its implementation.

Faster is not always more informative

If the source only changes once per minute, checking each second cannot manufacture newer evidence. On the other hand, a slow interval may create a confusing delay after an important action. Choose a freshness target from the user journey and the source's behavior, then measure the trade-off.

Push-based updates are another design option, not free capacity. They introduce connection management, reconnection, authorization, and missed-event recovery. Compare complete behavior rather than only the number of HTTP requests.

A review checklist

  • Count polling loops, including multiple tabs and widgets.
  • Define stop conditions and cleanup when leaving the page.
  • Prevent overlapping checks when a response takes longer than the interval.
  • Set a bounded retry policy for failures.
  • Keep last-observed state distinct from current fetch health.
  • Measure peak arrival rate as well as the average.
  • Recheck authorization for every observation.

A useful status screen is timely enough to support a decision and honest about the evidence it has. A shorter timer is only one part of that design.
